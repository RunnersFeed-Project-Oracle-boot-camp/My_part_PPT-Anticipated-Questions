# Runners Feed MVP 범위와 개인 기여

## 1. 문서 목적

이 문서는 Runners Feed 팀 프로젝트에서 실제로 구현한 MVP 범위와 개인 기여를 구분해 정리한다.

Runners Feed는 오라클 의료 바이오 AI 부트캠프에서 진행한 팀 프로젝트다.

최종 PRD, WBS, MVP 체크포인트와 발표자료는 팀 공동 산출물이며 내가 단독으로 작성한 문서가 아니다. 이 문서는 해당 자료와 공개 저장소·PR 기록을 바탕으로 구현 범위와 기여 경계를 다시 설명한다.

WBS는 프로젝트 초기에 작성한 계획 문서이므로, 담당자로 적혀 있다는 사실만으로 실제 완료를 주장하지 않는다. 개인 기여는 코드, 실험 결과, 저장소와 팀 PR로 확인되는 범위를 우선한다.

## 2. MVP 한 줄 정의

사용자가 측면에서 촬영한 짧은 러닝 영상을 업로드하면, 관절 좌표와 자세 특성값을 계산하고 측정 근거와 개선 행동을 리포트로 제공하는 러닝 자세 분석 서비스다.

## 3. MVP 사용자 흐름

```text
앱 실행과 소셜 로그인 시작 화면
→ 카카오·Google 계정으로 시작
→ 키 입력 및 촬영 가이드 확인
→ 영상 촬영 또는 선택
→ 형식·용량·길이 검증
→ Object Storage 직접 업로드
→ 비동기 분석 작업 생성
→ 단계와 진행률 확인
→ 자세 지표·그래프·코칭·관절 시각화 영상 확인
→ 기록에서 결과 재조회
```

지원 입력은 측면에서 전신이 보이도록 촬영한 한 사람의 짧은 러닝 영상이다. 최종 PRD 기준으로 앱은 MP4·MOV, 250MiB 이하, 3~10초 조건을 검증한다.

## 4. 팀이 구현한 MVP 범위

### 사용자 시작과 업로드

- 카카오·Google 계정으로 시작하는 소셜 로그인 UI
- 키 입력과 촬영 조건 안내
- 카메라 촬영 또는 갤러리 영상 선택
- 형식, 용량과 길이 검증
- 만료형 signed URL을 이용한 OCI Object Storage 직접 업로드

### 비동기 영상 분석

- 작업 생성과 `QUEUED`, `PROCESSING`, `SUCCESS`, `FAILED` 상태 제공
- RTMDet Nano 사람 검출
- RTMPose-M Halpe-26 관절 좌표와 신뢰도 생성
- RunPod GPU에서 영상 분석과 관절 시각화 영상 생성
- OCI에서 피처·리포트 후처리와 결과 검증

### 결과 제공

- 골반 수직진동
- 팔꿈치 각도
- 몸통 굴곡각
- 자세 기울기각
- 프레임별 변화 그래프
- 측정값과 기준에 연결된 코칭 행동
- 관절 움직임을 표시한 결과 영상
- 과거 작업과 성공 결과 재조회

### 운영과 데이터 관리

- 모델 ID와 immutable release 추적
- schema, checksum과 산출물 검증
- 입력과 임시 분석 산출물의 보관정책
- API, DB, Redis, Object Storage, 작업 단계와 호스트 자원 모니터링
- immutable 이미지 기반 배포와 운영 복구 절차

위 항목은 팀 전체가 구현한 제품 범위다. 모바일 앱, API, 모델, 데이터베이스와 운영 인프라 전체는 개인 단독 구현 범위가 아니다.

시작 화면에는 카카오·Google 계정으로 시작하는 방식이 표시됐다. 다만 최종 PRD에서 실제 계정 전환 구현 상태는 카카오 로그인이 운영 준비 단계로 기록되어 있으므로, 두 소셜 로그인 방식이 모두 운영 환경에서 완전히 검증됐다고 주장하지 않는다.

## 5. MVP에서 의도적으로 제외한 범위

| 제외 기능 | 제외 이유 |
|---|---|
| 실시간 자세 피드백 | 모델·앱·지연시간 검증 범위가 커져 업로드 기반 핵심 흐름 안정화를 우선했다. |
| 의료 진단과 부상 예측 | 2D 영상과 제한된 연구 기준만으로 의료적 판단을 제공할 수 없다. |
| 다중 인물 자동 지정 | 겹침과 오검출이 결과 신뢰도를 낮추므로 한 사람의 측면 영상을 지원 조건으로 정했다. |
| 웨어러블 연동 | 짧은 프로젝트 기간에 영상 기반 핵심 가치 검증을 우선했다. |
| SNS 공유·랭킹·유료 요금제 | 분석 결과 생성과 이해라는 핵심 사용자 흐름에 포함되지 않는다. |
| 서로 다른 촬영 영상의 임상적 변화 판정 | 카메라 각도와 거리, 가림, FPS 차이를 통제하지 않으면 직접 비교하기 어렵다. |

## 6. 분석과 피드백의 책임 분리

MVP의 설계 원칙은 LLM이 영상에서 근거를 직접 찾거나 자세를 판정하지 않도록 하는 것이다.

```text
관절 좌표와 신뢰도 추출
→ 자세 특성값 계산
→ 평가 기준 적용
→ 측정값·기준·판정·신뢰도가 포함된 구조화 결과 생성
→ LLM이 구조화 결과를 사용자 언어로 설명
```

LLM은 제공되지 않은 측정값이나 판단 근거를 새로 만들면 안 된다. 근거가 부족하거나 신뢰도가 낮은 항목은 확정적인 개선점으로 노출하지 않는 것이 목표다.

이 원칙은 팀의 MVP 체크포인트와 최종 PRD에 포함된 설계 방향이다. 개인 단독으로 정한 구조라고 주장하지 않는다.

## 7. 개인 기여

### 7.1 2D 영상에서 측정 가능한 피처 검토

- 러닝 생체역학 연구에서 사용한 지표를 측면 2D 영상과 Halpe-26 좌표로 계산할 수 있는지 검토했다.
- 지면반력, 관절 모멘트와 대사량처럼 별도 장비가 필요한 지표를 영상 측정 범위에서 제외했다.
- 거리 관련 값은 실제 길이로 단정하지 않고 신체 크기로 정규화한 비율로 다루는 방향을 검토했다.
- 연구 참고값을 의료 진단 기준이 아닌 비교용 정보로 구분했다.

초기 WBS의 평가 항목 연구, 평가 항목 선정과 판정 기준 검토가 이 업무와 연결된다. 실제 조사 내용은 논문 기반 피처 저장소와 프로토타입 기록으로 확인한다.

### 7.2 영상 처리 병목과 입력 형식 검증

- PNG와 JPEG 품질 95의 프레임 저장시간과 용량을 비교했다.
- 포맷 변경 후 Halpe-26 좌표 차이를 확인해 속도 개선과 결과 변화를 함께 검토했다.
- 동일 영상 255프레임 기준 저장시간은 17.69초에서 3.07초로 82.6% 줄었다.
- 저장용량은 902MB에서 186MB로 79.4% 줄었다.
- 평균 관절 차이는 1.986px였고 전체 keypoint의 94.4%가 3px 이내였다.

이 실험은 단일 영상 결과이며 화면 진입·퇴장과 반사 구간에 이상치가 있었다. 따라서 모든 영상에서 품질 영향이 없다고 일반화하지 않는다.

### 7.3 CPU·GPU 성능과 처리 경계 검증

- Grafana 단계 시간을 확인해 자세 추론과 영상 처리 병목을 구분했다.
- 추론만 원격 GPU로 이동한 임시 시험에서 전체 개선이 7.4%에 그친 것을 확인했다.
- GPU 책임 범위를 추론에서 디코딩·추적·렌더링·인코딩을 포함한 전체 `video_analysis`로 확장했다.
- OCI 업로드와 결과 다운로드를 포함한 GPU 왕복시간을 측정했다.
- 고정 입력 두 개에서 기존 CPU 대비 48.01%, 79.05%의 처리시간 단축을 관측했다.
- CPU·GPU 관절 좌표, 인원 검출과 출력 영상 메타데이터 차이를 함께 기록했다.

GPU가 빠르다는 사실과 앱에서 안정적으로 사용할 수 있다는 사실을 별도로 검증했다. 앱 적용 과정에서 발생한 데이터 계약과 배포 문제는 GPU 연산 성능만으로 해결되지 않았다.

### 7.4 RunPod 비동기 영상 분석 서버 구현

공개 커밋과 PR에서 확인되는 주요 구현 범위는 다음과 같다.

- `POST /v4/storage-video-analysis` 작업 등록과 HTTP 202 응답
- `remote_job_id` 기반 비동기 상태 polling
- `queued`, `running`, `complete`, `failed` 상태 계약
- 동일 `attempt_id` 재전달 시 기존 작업을 재사용하는 중복 추론 방지
- SQLite 기반 작업 상태 보존
- Bearer token 인증
- HPE·추적·보간·렌더링과 NVENC H.264 변환
- OCI Object Storage 산출물 업로드
- CUDA와 모델 release 증거를 포함한 manifest 생성

이 목록은 공개 코드와 PR 기록에 나타난 구현 범위를 요약한 것이다. 각 기능의 세부 동작과 설계 이유는 필요할 때 해당 코드와 함께 다시 확인한다.

초기 Object Storage 기반 통합은 팀의 브랜치 검토 절차를 맞추기 위해 PR #28에서 되돌렸다. 이후 비동기 서버로 다시 구현해 PR #34를 통해 팀 저장소 `main`에 병합했다.

### 7.5 팀 제품 반영과 운영 문제 대응

- PR #23: Object Storage 기반 RunPod 영상 분석 파이프라인
- PR #24: RunPod 프록시 User-Agent 적용
- PR #25: GPU 계약 UUID 문자열 정규화
- PR #26: systemd 동기화와 배포 디스크 보호
- PR #34: 비동기 RunPod 영상 분석 서버 재구현과 병합

PR 병합만으로 제품 적용이 끝난 것은 아니었다. UUID 직렬화, 프록시 요청, 배포 디스크와 systemd 권한 문제가 실제 통합 과정에서 발생했다. GPU attempt·DB 상태 계약, polling 간격, 모델 통합과 rtmlib 호환성 등의 후속 안정화는 팀 공동 작업으로 이어졌다.

## 8. 팀 구현과 개인 기여 경계

| 영역 | 팀 MVP 결과 | 개인 기여 | 단독 구현으로 주장하지 않는 범위 |
|---|---|---|---|
| 자세 피처 | 4개 자세 지표와 프레임별 결과 | 논문 조사, 2D 측정 가능성·근거·한계 검토 | 최종 피처 계산 코드 전체와 기준 승인 |
| 모델 | RTMDet·RTMPose 기반 자세 추정 | 프로토타입 실험, 입력·결과 차이 검증 | 모델 선정·개발·가중치와 최종 품질 승인 |
| 영상 성능 | RunPod GPU `video_analysis` 경로 | PNG·JPEG, CPU·GPU 실험과 처리 경계 설계 | 전체 OCI 인프라와 운영 구성 |
| RunPod 서버 | 비동기 GPU 분석 서비스 | 작업 API, 상태·중복 방지·상태 보존·manifest 구현 | 후속 DB 계약, 모델 통합과 안정화 전체 |
| 앱·리포트 | 업로드부터 결과 조회까지 사용자 흐름 | GPU 경로와 결과 산출물 연결에 기여 | 모바일 UI, 인증, 전체 API와 LLM 리포트 설계 |
| 운영 | 배포·모니터링·복구 구조 | 통합 중 발견한 오류 수정과 관련 PR | 팀 운영 인프라 전체의 단독 설계·구축 |

## 9. 현재 한계

- 카메라 각도, 거리, 가림, 모션 블러와 화면 진입·퇴장 구간이 관절 좌표와 피처에 영향을 준다.
- 착지와 toe-off는 2D 관절 좌표 변화로 추정한 이벤트다.
- 연구 참고값을 의료 진단이나 부상 예측 기준으로 사용할 수 없다.
- CPU·GPU 경계에서 특정 프레임의 인원 검출 차이가 확인됐다.
- CPU와 GPU 인코더의 화질 동등성을 VMAF·SSIM으로 검증하지 않았다.
- 성능 시험의 반복 횟수와 운영 표본 수가 적어 모든 영상과 환경에 일반화할 수 없다.
- 사용자 조사 21명은 문제 탐색 자료이며 서비스 효과나 시장성을 입증하지 않는다.

## 10. 정리

팀 MVP는 영상 업로드부터 비동기 분석, 측정값·코칭·관절 영상 확인과 기록 조회까지 하나의 사용자 흐름으로 연결했다.

개인 기여의 핵심은 팀 제품 전체를 단독으로 만든 것이 아니다. 2D 영상에서 측정할 수 있는 피처의 범위를 검토하고, 영상 처리 병목을 실험으로 확인했으며, 전체 `video_analysis`를 GPU로 분리하는 구조를 검증하고 비동기 RunPod 서버로 구현해 팀 제품에 반영한 것이다.

이 과정에서 GPU 처리 속도와 실제 앱 적용은 서로 다른 문제라는 점을 확인했다. 성능 수치뿐 아니라 결과 차이, 데이터 계약, 배포 문제와 후속 한계를 함께 기록한 것이 이 작업의 주요 기술적 판단이다.
